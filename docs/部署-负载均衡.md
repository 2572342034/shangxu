# 负载均衡部署说明（Nginx + 双后端实例）

> 目标：单机单实例扛不住时，横向扩后端实例，用 Nginx 分发流量，
> 并加限流与超时控制，避免单点变慢拖垮整个服务（雪崩）。

## 一、架构

```
浏览器
  │
  ▼
Nginx（frontend:80）
  ├─ 静态资源：/  /assets/        ← 直接返回，不进后端
  └─ /api/ → upstream crm_backend（least_conn）
                ├─ backend1:8080   ← 承担定时任务
                └─ backend2:8080   ← 定时任务关闭
                        │
                        ├─ MySQL（共享）
                        └─ Redis（共享，登录态）
```

后端不再对外暴露端口，只能经 Nginx 进入。

## 二、加负载均衡之前必须先满足的三个前提

**这三条不满足，加 Nginx 反而会制造 bug。**

### 1. 后端必须无状态 —— 已验证 ✅

登录态存在 Redis（`crm:login:{userId}`），不在 JVM 内存里。实测：

```bash
# 在 8081 登录
TOKEN=$(curl -s -X POST http://localhost:8081/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"username":"admin","password":"123456"}' | jq -r .data.token)

# 用同一个 token 访问 8082
curl http://localhost:8082/api/auth/info -H "Authorization: Bearer $TOKEN"
# → 200 {"nickname":"系统管理员"}

curl "http://localhost:8082/api/customers?pageNum=1&pageSize=3" -H "Authorization: Bearer $TOKEN"
# → 200 正常返回列表
```

**跨实例拿同一个 token 能通，说明可以随便分发。**

### 2. 定时任务不能重复跑 —— 已处理 ✅

`CrmScheduler` 加了条件注解，配置为 `false` 时 **Bean 根本不注册**：

```java
@ConditionalOnProperty(name = "crm.scheduler.enabled", havingValue = "true", matchIfMissing = true)
```

compose 里 backend1 为 `true`、backend2 为 `false`。这样即使有人误配成两个都 `true`，也只会在显式开启的实例上执行。

### 3. 附件存储必须共享 —— 单机 OK，多机需改造 ⚠️

附件走本地磁盘（`crm.upload.dir`）。当前方案：

- **单宿主机 + Docker 命名卷**：两个实例挂同一个 `shangxu-uploads` 卷，可共享 ✅
- **多宿主机**：A 机上传的文件 B 机读不到，下载会报「附件文件已丢失」❌

多宿主机部署必须换对象存储（MinIO / 阿里云 OSS）。改造点已经留好：`AttachmentService` 的 `uploadDir` 是配置项，把它抽成 `StorageService` 接口（`store` / `load` / `delete`）即可替换实现。

## 三、雪崩防护做了哪些事

光加实例不够，还要防止「一个慢请求拖垮整池」。Nginx 侧做了四件事：

| 手段 | 配置 | 作用 |
|---|---|---|
| **负载均衡策略** | `least_conn` | 优先给连接数最少的节点。轮询不看负载，慢节点照样被均分请求 |
| **快速失败超时** | `proxy_connect_timeout 3s`<br>`proxy_read_timeout 60s` | 后端卡住时网关不无限等，及时释放连接 |
| **限流** | `limit_req rate=30r/s burst=60`<br>`limit_conn 50` | 单 IP 每秒 30 请求、并发 50 连接封顶，挡住刷接口与爬虫 |
| **故障转移** | `proxy_next_upstream`<br>`max_fails=3 fail_timeout=30s` | 节点 5xx/超时时自动换节点；连续失败 3 次摘除 30 秒 |

导出类接口单独放宽到 180 秒并关闭 `proxy_buffering`（边生成边下发，不占网关内存）。

**没做的**：应用层熔断降级（Resilience4j / Sentinel）。如果后续要对接外部系统（如金蝶 ERP），调用超时可能拖住线程池，那时需要补熔断。

## 四、部署

```bash
cd /path/to/CRM系统

# 首次构建并启动（会构建两个后端镜像，实际复用同一层缓存）
docker compose up -d --build

# 查看状态
docker compose ps

# 验证网关
curl http://localhost/healthz
# → ok

# 验证负载均衡：连续请求，看日志落在哪个实例
for i in $(seq 1 6); do
  curl -s -o /dev/null http://localhost/api/health
done
docker compose logs --tail=20 backend1 backend2
```

预期：两个实例都能看到请求记录（`least_conn` 下大致均分）。

## 五、扩容到 3 个实例

1. `docker-compose.yml` 里复制一段：

```yaml
  backend3:
    <<: *backend-base
    container_name: shangxu-backend3
    environment:
      <<: *backend-env
      CRM_SCHEDULER_ENABLED: "false"
```

2. `deploy/nginx/nginx.conf` 的 upstream 加一行：

```nginx
server backend3:8080 max_fails=3 fail_timeout=30s;
```

3. 热加载，不用停服：

```bash
docker compose up -d backend3
docker compose exec frontend nginx -t && docker compose exec frontend nginx -s reload
```

## 六、参数调优参考

| 场景 | 调整 |
|---|---|
| 后端 CPU 吃紧 | 每实例 `JAVA_OPTS` 降 `-Xmx`，加实例数（当前 2×512M） |
| 数据库成瓶颈 | 加实例无用，先优化 SQL / 加索引 / 读写分离 |
| 用户集中同一出口 IP | `limit_req` 按 IP 限流会误伤，改成按用户 ID 限流（需 Lua 或应用层限流） |
| 导出大文件超时 | 调 `proxy_read_timeout`（当前 180s），或改成异步导出（提交任务 → 轮询下载） |

## 七、已知限制

1. **本机未做端到端验证**：开发环境没有 Docker 与 Nginx 二进制，配置未经 `nginx -t` 校验。上线前务必执行：
   ```bash
   docker compose exec frontend nginx -t
   ```
2. **MySQL 与 Redis 仍是单点**：Nginx 只解决应用层。数据库挂了照样全站不可用，生产需要主从 + 哨兵/集群。
3. **内存翻倍**：两个后端各 512M，加上 MySQL/Redis，建议宿主机至少 4G。
